# 2026-09-20: truthful call states QA (jes-11)

## Surprises worth keeping

- **Production guest auth needs an HTTPS origin locally.** `next start` + NextAuth
  issues `__Secure-` session cookies, so a plain `http://localhost` QA loop drops the
  session. A small self-signed TLS reverse proxy in front of the app port fixes it.
- **`/explore/[id]` streams, and the AgentCallGate subtree is briefly duplicated**
  (~200 ms, `[role=status]` count goes 0 -> 2 -> 1) before the streamed content
  settles. Playwright assertions must wait for the collapse, yet the localStorage
  mount guard still fires exactly one auto POST.

# 2026-09-20: Telegram bot adapter (apps/bot)

Implemented `.agents/plans/2026-09-20-telegram-bot-adapter.md` in worktree
`~/.worktrees/chezy-0/telegram-bot-adapter` (branch `feat/chezy-0/telegram-bot-adapter`).

## Open items, resolved

1. **Username into tool execute**: `requestContext` set in the `onDirectMessage`
   handler works. `tools/adapt.ts` reads `USERNAME_CONTEXT_KEY` from
   `ctx.requestContext`; no fallback needed.
2. **Proactive sends**: primary path works. `radar/sender.ts` tries
   `provider.getAdapter(installationId)` + `openDM`/`postMessage`, and falls
   back to raw Bot API `sendMessage` when no adapter is live. Both paths are
   coded; the radar test exercises the raw fallback (no connect in that test).
3. **Postgres memory**: `@mastra/pg` `PostgresStore` with `schemaName: "mastra"`
   works on pg0; no LibSQL fallback needed.

## Surprises

- `@mastra/telegram` sends **GET** requests when a Bot API call has no payload
  (getMe, deleteWebhook). The fake must handle `app.all`, not just POST.
- `editMessageText` must return a full Message object (`chat.id` included) or
  the chat SDK crashes reading `result.chat.id`.
- `toolDisplay` defaults to `text` on Telegram, which sets
  `canRenderApprovalButtons: false` and auto-resumes suspended tools. Set
  `toolDisplay: "cards"` to get approve/deny inline keyboards.
- The approval card is delivered as an `editMessageText` on the tool-call
  message, not a fresh `sendMessage`.
- `MastraLanguageModelV2Mock`'s `doStream` array form indexes AFTER pushing to
  `doStreamCalls` (element 0 is skipped). Use a function returning queued
  results instead.
- Channel DM round-trip (placeholder -> streamed edit) takes ~8s against pg;
  tests need generous timeouts.
- Telegram installations persist in Mastra storage: tests must
  `disconnect("chezy")` between runs.
- Streaming replies arrive as `rich_message.markdown` in `editMessageText`,
  not `body.text`.

## Deviations from the plan

- `apps/web/lib/ai/tools/{record-listing-feedback,arrange-viewing}.ts` do not
  exist in the repo; the allowed web edits (one `*Input` export per file)
  covered only `search-listings.ts` and `save-user-profile.ts`. Bot-local
  equivalents live in `apps/bot/src/tools/record-feedback.ts` and
  `arrange-viewing.ts`, mirroring the web route logic (`/api/viewing`,
  VIEWING_MODE mock/slng/vonage) and recording dispatches in `bot.viewings`.
- `apps/bot/src/env.ts` accepts both `TELEGRAM_BOT_TOKEN`/`TELEGRAM_BOT_API_KEY`
  and `TELEGRAM_BOT_USERNAME`/`TELEGRAM_BOT_NAME` (the credential file uses the
  `*_API_KEY`/`*_NAME` spellings). dotenv loads `apps/bot/.env` + `.env.local`
  in `src/index.ts` only; env.ts still falls back to `apps/web/.env*` for
  shared vars so tests work.
- `dispatchViewing` records a `bot.viewings` row for failed dispatches too, and
  mock mode does not require a callee.
